## 1. 총평

2차 보고서(2026-09-16, 확정 102건)와 같은 커밋을 대상으로 finder 가 이전 지적을 먼저 읽고 신규 결함만 찾도록 구성했다. 그 결과 **133건이 추가로 확정**됐다(critical 0 / major 25 / minor 108). 2차와 비교하면 신규 건은 "특정 조건에서만 드러나는" 유형이 많다 — 표시 단위 psig, 소수점이 쉼표인 로케일, 창을 닫지 않은 채 두 번째 사이클 진행, 장비의 명시적 거부 응답, 기준 refresh 가 끝나기 전의 창 조작 등. 반대로 말하면 기본 설정(Torr, 자릿수 3, 정상 응답)에서는 대부분 보이지 않으므로 현장 보고로 드러나기 어렵고, 그만큼 오래 잠복한다.

가장 위험한 것은 네 묶음이다.

첫째, **쓰기 실패가 성공으로 보이는 경로**(N009, N045, N056). NV2 RW 쓰기의 응답은 아예 판정하지 않아 장비의 거부 코드(78/80/76)가 INFO 트랜잭션으로만 남고, 재부팅 유발 param(Restart Controller / Restore Factory Parameters)은 거부 응답이든 통신 오류든 재부팅 대기로 들어가 1초 뒤 probe 성공을 '재연결 완료' 로 만든다. 펌웨어 창은 이를 'factory reset completed' 로 안내하고 백업 복원 창까지 연다 — 초기화되지 않은 장비에 백업을 복원하는 경로가 실제 워커·창 객체로 재현됐다.

둘째, **psig 표시 단위 계열**(N079, N100, N120, N093, N105). "표시 단위의 0 = 절대 0" 가정이 차트 Full 범위, 압력 setpoint 창, 변화율 위젯, 설정점 버튼에 흩어져 있어, Unit 콤보에서 psig 를 고르는 순간 곡선이 화면 밖으로 나가고 진공 설정점을 만들 수 없으며 Ramp Slope 는 760 Torr/sec 만큼 어긋난 값이 전송된다. F049 의 'Torr 도메인 비율' 수정만으로는 닫히지 않는다.

셋째, **편집값·설정값 손실**(N092, N118, N096). 다른 창의 refresh 가 편집 중인 RW 위젯을 장비값으로 되돌리고 dirty 를 지우며(Parameter 싱글턴 + notify_synced 발신자 미구분), 로컬 설정 창의 Apply 는 Enter 전 미클램프 텍스트를 그대로 저장해 범위 밖 설정점이 파일에 영구히 남고, ParamWin Save 는 Unknown 을 null 로 저장해 Load→Apply 가 무음으로 끝난다.

넷째, **최신 기능이 동작하지 않는다**(N095, N008). ADC Calibration 창(WO param 만 있는 ParamWin)은 refresh 가 EMPTY 로 끝나 본문이 영구 잠기고, NV1 WO 쓰기에 'E:' 응답이 한 번 오면 param 이 세션 내 복구 불가능한 Not Support 로 잠긴다. 둘 다 실장비 미검증 신규 경로라 첫 현장 시험에서 그대로 드러난다.

그 밖에 배포·빌드 쪽에 실무적으로 즉시 걸리는 것이 있다: build.bat 이 매 빌드 PyInstaller 확인 프롬프트를 띄우고(Enter 면 실패, N125), FTP 계정/비밀번호가 소스·배포 exe·소스 스냅샷에 평문으로 실리며(N064), %TEMP% 경로에 `&` 가 있으면 앱 업데이트가 앱만 종료한 채 끝나고(N062), 펌웨어 다운로드 캐시(temp/*.dlla)가 git·배포·앱 업데이트를 타고 현장의 최신 펌웨어를 옛 파일로 덮는다(N046).

2차 보고서의 사실 관계나 수정 제안을 정정해야 할 것이 9건 나왔고(6절), 프로젝트 메모 2건(백업/복원 설계 메모의 '중복 줄·재부팅 param' 정책, 규칙 목록의 c_values 템플릿 문구)이 코드보다 낡아 있음이 확인됐다.

설계 검토(5절)의 결론은 **"뼈대는 유지, 경계 한 층 바깥의 계약을 강화"** 다. 4관점 28개 제안을 3인이 심사해 8개로 압축했고, 그중 5개(로그 매니저 재진입 가드, JSON 원자 저장 헬퍼, WinManager 등록부 확정, SerialSetting 타입, 컨버터 시그널 3분리)는 이미 확정된 F 수정의 '형태' 그 자체라 F 수정과 동시에 하면 되며, 창 골격 분할(ServiceWin/ParamWin)과 spec 결과 객체화는 테스트 하네스를 먼저 만든 뒤가 안전하다. 워커 5종 공통 베이스, firmware 워커 5분할, 백업 값 기반 형식 전환, 차트·로컬 설정 창 골격 추출은 하지 않는 것이 맞다고 판단했다.

**이번에 다시 확인된 긍정 사실**(재검사 불필요): 펼친 3,550 path 에 중복·공백·대소문자 충돌 0, enum 참조 876건 전부 존재, enable 조건 199건 참조 정합, NV1 샘플 응답 8건 payload 41자 정합, `tools/test_packetspec_step1.py`(126,416 체크)·`test_nv1_step4.py`(6,363)·`test_nv1_step6.py`(708) 전부 통과, EtherCAT 템플릿의 `%1` 72개가 전부 마커 다음 줄에 있어 치환 잔여 0, `tables.py` 의 WrapHeaderView 는 열 폭 변경에 무한 재귀 없이 수렴, `write_only_values.py` 는 범위 밖 텍스트를 Enter 없이 Send 해도 fixup 클램프 후 전송(F064 류 해당 없음).

## 2. 우선 조치 목록 (major 25건, 전건 재현)

순서는 '장비에 잘못된 값이 가거나 잘못된 성공 안내가 뜨는 것' → '기능 불능' → '배포·빌드' → '조건부 UX' 다. 각 건의 근거 줄 번호와 재현 스크립트 경로는 검증 기록(final_result.json)에 있으며, 표의 제안은 R3(중복 안전망 금지)을 지키는 최소 수정이다.

### A. 쓰기 실패가 성공으로 보이는 경로

- **N009 `b_core/g_protocol/nv2_spec.py:103` — RW param 의 NV2 쓰기 응답 무판정.** `_check_response` 는 `is_read=False` 이고 `acc != WO` 이면 응답을 보지 않고 `(NONE, False)` 를 돌려준다. 장비의 `p:78…`(NOT_ALLOWED_IN_THIS_STATE)·`p:80…`·`p:76…` 은 물론 쓰레기 응답까지 INFO 트랜잭션으로 기록되고 read-back 은 dirty 만 남긴다(왜 반영이 안 됐는지 어디에도 없음). 같은 응답이 WO 면 ERR_78 로 매핑되는 것과 대비. 실제 워커 WRITE 분기에 응답 주입으로 재현. → 오류 코드(`resp[2:4] != '00'`)를 ERR_CODE_MAP 으로 매핑해 돌려주고(need_retry False, 시퀀스 계속), 시퀀스 종료 시 '거부된 param 목록' 1회 요약. F042 와 같은 파일이므로 함께 처리.
- **N045 `b_core/e_worker_ver2/parameter_run_worker.py:704` — reconnect param 쓰기가 실패해도 재부팅 대기 진입.** WRITE 결과에서 err_type/param_err_type 을 로그만 남기고 `is_need_reconnect` 면 무조건 `_start_reboot()`. 포트가 닫히고 전 창이 끊김 표시된 뒤 1초 probe 가 (재부팅하지 않은) 장비 응답을 받아 재연결·전체 refresh — 정상 경로와 화면이 동일하다. 실제 워커 스레드 + FactoryFirmwareUpdateWin 으로 거부 응답·통신 오류 두 경우 재현. → 재부팅 대기 진입을 `err_type == NONE and param_err_type == NONE` 으로 한정하고, 실패는 시퀀스를 정상 종료하며 창이 알 수 있는 시그널(예: sig_write_failed)을 낸다. 타임아웃(응답 없음)만 기존대로 재부팅 가정.
- **N056 `c_ui/c_window_ver2/g_factory/factory_firmware_update_win.py:505` — Factory Reset 거부가 '완료' 로 안내.** 위 결함의 창 쪽 결과: `write()` 의 StartResult.OK 만 보고 FACTORY_RESET 단계로 넘어가며, 장비가 `p:78` 로 거부해도 probe 성공 → refresh → "Firmware update and factory reset are completed." + RestoreWin 자동 오픈. 가짜 장비로 end-to-end 재현. → 워커의 실패 시그널을 받아 FACTORY_RESET → IDLE 복귀 + 실패 안내(LogView 안내).

### B. psig 표시 단위 (표시 단위 0 = 절대 0 가정)

- **N079 `c_ui/a_converter/pressure_converter_manager.py:126` — `get_dp_max_pres()` 가 psig 에서 음수.** 만압 100 Torr → -12.76 psig, 760 Torr → -4.6e-08. 차트 Full 모드가 `(0.0, full_max)` 로 쓰므로 `y_max <= y_min` 가드로 (0, 1) psig 로 퇴화. → 만압 '구간' API(`get_dp_full_range()` = `(to_display(0 Torr), to_display(max))`)를 두고 소비자가 그 구간을 쓴다. docstring 에 오프셋 단위에서는 절대 상한이 아님을 명시.
- **N100 `c_ui/c_window_ver2/a_main/main_chart_panel.py:619` — 차트 FULL 하한 0.0 고정** (SensorAnalysisWin `sensor_analysis_win.py:437` 은 N115, 같은 뿌리). Full 은 기본값이라 Unit 콤보에서 psig 를 고르는 순간 10 Torr = -14.50 psig 곡선이 화면 밖. 실제 ViewBox 로 재현(FS1000 → (0, 4.64), FS760 → (0, 1)). → 하한을 `to_display(0.0 Torr)` 로, 상한은 `get_dp_max_pres()` — 두 창 모두.
- **N120 `c_ui/c_window_ver2/x_localsetting/local_pres_setting_win.py:37` — setpoint 행 하한 0.0(표시 단위) 고정.** psig + 만압 < 760 Torr 이면 6행 전부 빈 칸('Unknown') 활성 상태가 되고 validator 가 '-' 를 거부해 이 창에서 진공 설정점을 만들 수 없다(재현 인자 psig/100 Torr). → 하한을 `to_display(0 Torr)`(단위 변경 시 재적용) 또는 -FLOAT32_MAX 로 두고 물리 검사는 sfs 변환 결과로. F098 의 컨버터 구독을 넣을 때 범위 재설정을 함께.
- **N093 `c_ui/b_control_ver2/d_param/param_values.py:549` — 변화율(slope) 위젯이 압력 변환(gain+offset)을 그대로 상속.** psig 에서 장비값 10 Torr/sec 가 -14.50 psig/sec 로 표시되고, 1 psig/sec 입력 후 Apply 하면 811.7 Torr/sec 가 전송된다(RO Actual Slope, 백업 unit 환산 동일). psig 일 때는 사용자 개입 없이 상시. → 차분량용 변환(`to_display_delta/from_display_delta`, gain 만) 추가. 결정 J 가 표시 오프셋까지 '현행 유지' 라면 docstring 에 명시.
- **N105 `c_ui/c_window_ver2/a_main/main_pressure_panel.py:164` — 설정점 버튼이 버튼 텍스트(자릿수 반올림)를 재파싱해 전송** (위치 패널 `main_position_panel.py:120` 은 N102, 백분율이라 오차 작아 minor). 만압 1000 Torr, bar, 자릿수 1, 설정점 500 Torr → 버튼 "0.7" → 525 Torr 전송(+5%); 자릿수 0 에서 0.5 Torr 설정점 → 0 Torr. 실제 패널 슬롯 경로로 재현. → 슬롯에서 LocalSetting 값을 직접 변환(`convert_sfs_to_dp_pres(setpoint) → from_display`), 버튼 텍스트는 표시 전용.

### C. 편집값·설정값 손실

- **N092 `c_ui/b_control_ver2/d_param/param_values.py:37` — 다른 창의 refresh 가 편집 중인 RW 위젯을 되돌리고 dirty 를 지움.** `_bind_param` 이 sig_synced/sig_value_changed 를 모두 set_value+commit 에 연결하고, 워커는 자기 refresh 의 읽기 성공마다 spec.params 전부에 notify_synced. ## 5. 설계 방향 검토

사용자의 질문 "더 좋은 설계 방향이 있는지" 에 대한 답이다. 4 관점 검토자가 코드를 직접 읽고 낸 28개 제안을 심사자 3인(현장 운영·1인 유지보수 부담 / 코드 정합성·회귀 위험 / 사용자 선호·규칙 적합과 순서)이 독립 채점했고, 겹치는 제안을 합쳐 8개로 압축했다. 확정 규칙(R1~R5)과 사용자 선호(틀 먼저, 액션별 전용 슬롯, GUI 최소, 도메인 경계)는 제안의 전제로 두었다.

### 5.1 진단

뼈대는 건강하다 — 값(Parameter) / 규약(PacketSpec) / 바인딩(SpecRegistry) / 전송(ServicePort) 4분리가 실제 import 그래프와 코드에서 지켜지고, b_core→c_ui 역참조 0건, ServicePort 는 프로토콜을 모르며, 워커 수명·seq 늦은 응답 폐기·스키마 오류 종료 계약 같은 2차 6절의 강점은 이번 4관점 검토에서도 그대로 확인됐다. 구조적 약점은 네 군데로 모인다.

1. **경계 한 층 바깥의 견고성 공백** — 설정 파일 제자리 'w' 덮어쓰기(F010), 로그 매니저가 자기 구독자의 예외에 재진입해 프로세스를 죽이는 경로(F007), 앱 업데이트의 사전 검사·롤백·결과 기록 부재(F036/F094, N062).
2. **spec ↔ 워커 결과 계약이 느슨함** — 튜플 + 부수효과 + '예외 없음' 약속 없음. 잡음 응답 한 건이 상태 머신을 세우고(F041/F032), 플래그 대입 위치가 NV1/NV2 에서 갈리며(F042), RW 쓰기 응답은 판정조차 없고(N009), 실패해도 재부팅 대기로 들어간다(N045).
3. **ParamWin 이 '폴더 카드 창' 이 아니라 앱 표준 창 골격으로 쓰임** — 상속 10개 중 c_window_ver2 창 7개, takeCentralWidget 6곳, 클래스 기본값 hack 7곳. 그래서 d_param 이 c_window_ver2 를 역참조하고(F061), 잠금 결정이 4곳으로 흩어지며(F081, N095, N072), 시리얼 설정 변환표 3벌·6-튜플 조립 18곳처럼 d_dal 에 타입 하나가 없어 생긴 복제가 있다(F014/F018/F025).
4. **검증 수단이 막혀 있음** — 헤드리스 창 테스트가 배포 설정 파일을 오염시키고(F001), 워커 상태 머신에 대역 이음새가 없어(F110) 구조 변경을 자동으로 확인할 길이 없다.

위험은 '큰 재작성' 이 아니라 두 가지다: 검증 수단 없이 파일 이동·상태 머신 수정을 먼저 하는 **순서 오류**, 그리고 사용자가 이미 폐기한 계약(c_values `set_value(is_commit)` 템플릿)을 낡은 규칙 문구에 따라 되살리는 것.

각 제안의 핵심:

- **1위** — 매니저 내부 계약만 바꾼다(구조 변경 0). `threading.local` 플래그로 log()~emit 구간을 표시하고 `_StderrTee.write` 는 로깅 중이면 원본 stderr 로만 흘린다. emit 은 try 로 감싸 슬롯 예외를 `sys.__stderr__` 에 1줄 요약. `_write_file` 실패는 `_file_error` + 링버퍼에 ERROR 1회, 재시도는 날짜가 바뀔 때만. `parameter.py` 의 모듈 로거(사용처 0)를 지우면 b_datatype→c_manager 역참조와 하네스의 격리 순서 제약이 함께 사라진다. `_StderrTee._buffer` 는 짧은 Lock 으로 보호(N025).
- **2위** — `save_json_atomic(path, data)`(같은 폴더 .tmp → flush+fsync → os.replace, PermissionError 1회 재시도) / `load_json(path)`(형태·타입 검증, N026·N027) / `quarantine_corrupt(path)`. 두 매니저의 `_save` 는 bool 을 반환하고 `_Setting.__set__` 은 저장 실패여도 메모리·시그널을 유지한다. debounce 는 도입하지 않는다('대입 즉시 저장' 유지, 원자 쓰기만으로 kill-safe).
- **3위** — WinManager 의 역할을 '(win_id → 창) 등록부 + 생성/재활성/start 훅/전체 닫기' 로 문서화하고 메서드를 `show_window`(created 여부 반환) / `close_all(exclude=()) -> bool` / `param_win_id(path_or_name)` 셋만 둔다. MainWin.closeEvent 는 `close_all()` 이 False 면 ignore(F073). HelpNvmUpdateWin 은 launch 전에 `close_all(exclude=(self,))`, 거부면 IDLE 복귀(F094) — topLevelWidgets 순회는 순서가 비결정이고 버튼 없는 QMessageBox 가 close 를 거부해 quit 이 무음 중단되므로(N068, N110) 등록부 쪽으로 통일한다. 배치 스크립트 트랜잭션/저널(F036/F037/F034)은 배포 exe 3경로 실검증 세션 뒤 2차로.
- **4위** — `b_core/d_dal/serial_setting.py` 의 `SerialSetting`(NamedTuple 6필드)이 `from_connection`(connections.json 키 이름을 아는 유일한 곳) / `pyserial_kwargs()` / `term_bytes` / `describe()` 를 소유하고 변환표와 폴백 정책은 이 모듈 한 곳. `probe_once(setting, packet)` 가 임시 raw 포트 1왕복을 맡아 재부팅 probe 와 COM 스캔이 공유. `ServicePort.open(setting)` 은 SerialSetting 을 받고 `setting` 프로퍼티로 6-튜플 스냅샷을 대체. 재부팅 probe 는 `sn_spec.expected_response_prefix` 로 판정(F026). ServicePort 는 여전히 프로토콜을 모른다(C6). `ServicePort.open` 호출부는 2곳뿐이고 tools 테스트 3종은 open() 을 부르지 않아 영향 없음.
- **5위** — `isolate_runtime()`(TemporaryDirectory 에 config 복사 + path_def 5개 상수 덮어쓰기; 매니저 3종이 호출 시점에 path_def 를 읽으므로 코드 수정 불필요) / `Report`(상한 통일) / `make_app(offscreen)` / `fake_connected(svc)` / `assert_no_zombie(win_factory, singleton_signals)`(F111). `ParameterRunWorker(…, transport=None)` → `ParameterThread(transport)` 로 request_string 호출 3곳을 한 지점에 모아 {요청: 응답} 스크립트로 refresh→MONITOR, 잡음 재시도, PENDING 해제, 끊김, refresh 중 write BUSY 를 단언(F110). 폴더 분리(`tools/migration/`, `tools/tests/`, `tools/fixtures/`, `tools/run_tests.py` 서브프로세스 실행)와 러너 틀은 사용자가 먼저 잡는다. FakeSerial 은 만들지 않는다. 선행: F001 잔재 설정값 되돌리기(사용자 커밋). 착수 전 4절 12 의 워커 잠복 결함 4건 정리.
- **6위** — 0단계: 워커의 apply_response 호출 3곳(시퀀스 읽기/쓰기, 모니터)을 try/except 로 감싸 예외를 WRONG_FORMAT + need_retry 로 바꾸고 repr(e) 를 LogView 에; NV2 값 구간 실패에서 is_err=True(F042); RW 쓰기 오류 코드 매핑(N009); 재부팅 대기 진입 조건(N045); Nv1WriteSpec.build_request 의 세 return None 앞에 사유별 로그(F040); NV1 WO E: 응답은 is_err 로(N008). 본안: PacketSpec 에 Verdict(OK/TRANSIENT/NOT_SUPPORT/REJECTED)·Outcome·BuildFailure(VALUE_MISSING/CONTEXT_NOT_READY/BAD_VALUE) 를 두고 하위 클래스는 `_judge(resp)` 만 구현, 기본 클래스가 예외 방어 + verdict→플래그 규칙을 한 곳에서 적용. Verdict/BuildFailure 이름표와 플래그 규칙표는 사용자가 먼저 확정. step1 차등 테스트 126,416건 재기준화는 5위의 픽스처 전환과 같은 시기.
- **7위** — `PresConverterManager` 에 `sig_display_unit_changed / sig_decimals_changed / sig_full_scale_changed` 와 원인별 핸들러 3개(N078 이름 정정 포함). 구독 배선: MainChartPanel — unit → clear+범위 / decimals → 축 폭만 / full_scale → Full 범위만; 압력 위젯 — unit → 라벨+재표시, decimals → set_decimals; LocalPresSettingWin — unit + full_scale(F098, N120 범위 재설정 포함); SensorAnalysisWin — unit 만 clear(N114). 여기에 구간 API `get_dp_full_range()`(N079) 와 차분 API `to_display_delta/from_display_delta`(N093) 를 더한다. 기존 합집합 시그널은 이관 후 삭제. 연결은 전부 바운드 메서드(C1).
- **8위** — `c_ui/c_window_ver2/service_win.py` 에 ParamWorkerWinMixin(그대로 이동) 과 `ServiceWin(QMainWindow)`: BaseToolBar + BaseStatusBar + ParameterRunWorker 소유·1:1 연결(`with_param_worker=False` 로 생략 가능, HelpAboutWin) + svc_port 구독 + closeEvent cleanup + `has_refresh` + `_sync_lock_state()` 잠금 단일 지점(`content_widget.setEnabled(not (working or _edit_locked))` + `locked_actions()` 가 돌려준 액션을 working 중 비활성). 초기 연결 동기화는 __init__ 에서 빼고 `ServiceWin.start()` 로 옮겨 WinManager.show_window 가 생성 직후·show 직전에 1회 호출 — 서브클래스 __init__ 이 끝난 뒤라 클래스 기본값 hack 7곳이 사라지고 N095(EMPTY 잠김)·N072(트리 미잠금)이 뿌리에서 닫힌다. `ParamWin(ServiceWin)` 은 `c_ui/c_window_ver2/param_win.py` 로 옮겨 폴더 카드·Save/Load/Apply·enable 조건 배선만 남기고, 폴더 카드가 필요 없는 6개 창은 ServiceWin 직계, Iface 2종은 `e_iface/` 로. d_param 에는 param_folder_widget/param_values 만 남아 C3 가 완전히 성립. 골격과 `start()/locked_actions` 계약은 사용자가 먼저 작성하고 7개 창 이관은 Claude 가 채운다. 부분 적용 가능(ServiceWin 신설 → 6개 창 이관 → 파일 이동).

### 5.3 유지가 맞는 것 (검토자·심사자 일치)

- b_core 접두를 정렬용으로 두고 엄격한 계층으로 승격하지 않음 — 모듈 수준 순환 없음, 유일한 공통 뿌리는 AppLogManager, 접두를 의존 규칙으로 바꾸면 무해한 참조까지 뒤집어야 하고 얻는 것이 없다.
- 창마다 ParameterRunWorker(QThread) 를 하나씩 소유하는 구조와 워커 5종의 서로 다른 스레딩 골격 — 창 수명 = 워커 수명, 창별 seq 격리·log_source, 기준 워커 PENDING 게이트가 1:1 소유를 전제. 장수명 큐 / 최대 속도 폴링 / 단발 작업은 다른 물건이라 억지 통합하면 교체 지점이 흐려진다(F022 는 is_aborted·cleanup() 이름 통일만).
- ServicePort 의 락 2단 분리와 메인 스레드 단일 배달, ServicePort 가 문자열만 아는 것, 스키마 로더의 'load_errors → 대화상자 → sys.exit(1)' 계약.
- SpecRegistry 를 ParamManager 와 별개 싱글턴으로, param 객체를 dict 키로, 큐 생성 시 1회 resolve(2,679개 0.1ms 실측), Parameter 의 value/str_value 두 필드, NV2 1:1 / NV1 1:n 비대칭, codec 이 문맥을 호출 시점에 읽는 방식, Nv1WriteSpec 의 read-modify-write 와 전송 직전 encode — 대칭화·스냅샷·사전 조립은 확정 결정(E, 6) 과 반대 방향.
- x_message '표시 전용' 컨셉과 창 안의 QMessageBox 직접 호출의 공존('결정은 창 몫' 이지 '모든 박스는 x_message' 가 아님), 컨버터 2종이 c_ui 의 시그널 달린 싱글턴인 것(2026-09-08 배치 확정).
- 툴바 액션 47개 1:1 connect 와 thin 위임 슬롯, ParamWin 의 enable 조건을 '이 창의 위젯' 으로 한정하는 정책, d_param 의 RO/RW/WO 거울 클래스 쌍 26개(제네릭 바인더로 되돌리지 않음), c_values 의 'None → placeholder' 의미론과 스핀박스 예외.
- BackupWin/RestoreWin 트리 골격 45줄 중복(정책 분기가 다름), MainChartPanel(LocalSetting) 과 SensorAnalysisWin(창 로컬) 의 이원 상태 정책, ClusterMonitorWin 의 셀 위젯 없는 표 갱신, CompoundPollThread 의 `_config_gen` 세대 검사.
- 백업 파일이 선로 원문(p:01 패킷)이고 복원 창이 spec 과 독립인 것(R5) — NV1 param 이 백업 대상이 되는 시점(결정 10)에 사용자가 재검토.
- AppLogManager 를 파이썬 logging 으로 바꾸지 않는 것(TX/RX/INFO/WARN/ERROR 는 레벨이 아니라 종류), '대입 즉시 저장'(debounce 없음), 매니저 싱글턴 패턴과 path_def 모듈 속성 참조, 배치 스크립트 기반 앱 교체(부족한 것은 트랜잭션/저널이지 도구가 아님).
- `firmware_run_worker.py` 의 FTDI/파서/커널 링크 동거(F020) — F021/F024 를 현 파일 안에서 고치고 실장비 검증을 마치는 것이 먼저. 헤드리스 창 테스트가 실제 스키마를 읽는 것(격리 대상은 로그/설정 파일뿐).

### 5.4 제안됐지만 하지 않는 것

- **c_values `set_value(value, is_commit)` 템플릿 부활** — 규칙 목록 R5 의 그 문구는 낡았다. 사용자가 2026-08-10 본인 재설계로 'commit() = 현재 화면값을 ori_value 로 확정, 템플릿/last_set_value/짝 강제 전부 폐기' 로 바꿨고 현재 `base_value.py` 에 is_commit 은 0건이다. F058/F060/F064 는 템플릿 없이 좁힌 형태로: 활성 상태를 `_sync_enabled()` 한 곳(not is_not_support AND 값 기준 AND enable 조건)에서 계산, `set_not_support(False)` 시 마지막 값 재표시, `is_editable()` 로 Apply 수집을 거른다 — 이 설계도는 사용자가 틀을 제시한 뒤 채운다(선제 구현 금지 메모). **규칙 목록의 R5 해당 줄과 ver2-refactoring-plan 메모를 갱신할 것.**
- **firmware_run_worker.py 5조각 분리** — 플래시 커널 링크의 바이트 규약 이동은 한 바이트 실수가 장비를 벽돌로 만들 수 있는데 실장비 검증 수단이 없고, 분리 모듈의 두 번째 사용처가 없다(심사 3인 일치 reject).
