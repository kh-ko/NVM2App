## 1. 총평

전반 품질은 2026-09-08 보고서 시점보다 뚜렷이 올라갔다. 값(Parameter)/전송 규약(PacketSpec)/바인딩(SpecRegistry) 3분리가 실제 코드에서 지켜지고, ServicePort 의 락 2단 분리와 메인 스레드 단일 배달, 워커의 seq 기반 늦은 응답 폐기, 싱글턴 시그널의 바운드 메서드 연결(람다 0건), 워커 소유 창의 closeEvent cleanup 이 c_ui 전체에서 예외 없이 지켜진다. 이번에 확정된 102건 중 critical 은 없고 major 27건, minor 75건이며, 다수는 "실행해도 조용히 지나가는" 유형(안내 없는 실패, 상태 잔존, 표시 불일치)이다.

가장 위험한 것 세 가지는 다음과 같다. 첫째, **F007** — sig_logged 구독 슬롯이 예외를 한 번 내면 stderr 후킹을 타고 지수적으로 재진입해 약 11초 뒤 프로세스가 스택 오버플로(0xC00000FD)로 죽는다(실측). 둘째, **앱 업데이트 설치 경로(F017/F036/F094)** — 압축 해제 중 Abort 가 무시되어 설치·종료가 진행되고, 복사 실패 롤백이 _internal 만 되돌려 새 exe + 구 _internal 혼합 상태가 남으며, quit() 이 거부돼도 설치 스크립트는 이미 기동돼 30초 뒤 실패한다. 셋째, **F010** — local_setting.json/connections.json 을 제자리 'w' 로 덮어써 정전·강제 종료 시 설정 전체가 기본값으로 확정된다. 그 밖에 F021(USB 어댑터 EEPROM 을 식별 없이 프로그래밍), F041/F032(잡음 응답 한 건으로 워커 상태 머신 정지), F028(쓰기 중 Refresh 가 남은 쓰기를 무음 폐기)이 장비 운용 관점에서 중요하다.

이전 보고서 대비: 3.1(ServicePort 경합), 3.3(MainWin closeEvent 부재로 인한 크래시), 1.4-2(호출부 인자 불일치), 2.2.1(컨버터 배치)은 해소됐다. 1.4-1(show_param_window 중복), 2.2.2(믹스인 역참조), 3.4(스캔 블로킹)는 그대로 남아 이번에 다시 보고했고, 3.3 은 크래시가 아닌 UX 잔여(F073)로 좁혀졌다. 새 코드(NV1/PacketSpec, Cluster Monitor, ADC Calibration)에서는 규칙 6 위반 0건이었으나 "호출부 미갱신" 유형이 1건(F101) 재발했다.

**[F007] sig_logged 슬롯 예외가 stderr 후킹을 타고 무한 재귀 → 프로세스 크래시** — `b_core/c_manager/app_log_manager.py:242`

> repro: "exit code -1073741571 (0xC00000FD = STATUS_STACK_OVERFLOW) … 로그 파일 504줄 … 원인 예외(ValueError: boom)는 로그 파일에 0회 등장"

## 4. 패턴성 이슈

1. **시리얼 설정 변환표 3벌 + 폴백 상이 (F014, F018, F025)** — `service_port.py:119`, `parameter_run_worker.py:153`, `comport_scan_run_worker.py:25,41`. 스캔은 PARITY_EVEN, open/probe 는 PARITY_NONE. raw 포트 열기도 워커 2곳. 한 함수로 모아야 스캔 결과와 실제 연결이 갈라지지 않는다.
2. **고정 소수점 포맷 3벌 (F048, F050)** — float_util(f-string), inputs._format(f-string 재구현), 컨버터(Decimal half-even). 같은 값이 RO/RW 에서 마지막 자리가 다르다. float_util 헤더의 '단일 구현' 선언과 불일치.
3. **spec 응답 처리의 예외 무방비 (F032, F041)** — nv2_spec 의 int() 와 워커의 apply_response 호출 양쪽 모두 try 가 없어, 한 건의 잡음 응답이 시퀀스·모니터링을 정지시킨다. spec 계약을 "예외를 던지지 않는다"로 못박고 워커도 방어해야 한다.
4. **위젯 활성 상태를 여러 곳이 제각기 결정 (F058, F060, F064)** — set_not_support 는 True 만, set_value 는 무조건 setEnabled(True), on_enable_condition_changed 는 is_not_support 를 모르고, Apply 는 enabled 를 보지 않는다. 한 곳에서 (not is_not_support and 조건) 을 계산하는 구조로 모을 필요가 있다.
5. **스키마 로더의 '예외 없이 load_errors 수집' 계약 공백 (F012, F013, F044, F046, F101)** — params.json 의 type/acc 오타는 조용히 통과하고, Parameter 생성 예외·UnicodeDecodeError·비-객체 노드는 대화상자 없이 종료하며, 대화상자 파일 목록엔 nv1 이 빠져 있다.

## 6. 잘 된 점

1. **값/전송 규약/바인딩 3분리가 실제로 지켜진다** — 워커는 build_request/apply_response 만 쓰고 'p:'·'i:93' 을 모르며, codec 은 스키마 경로를 모른다. 펼친 params 3,550 / nv2 2,799 / nv1 read 60·write 91 이 전부 path 로 정합(미참조 0, 미존재 0).
2. **ServicePort 락 2단 분리 + 메인 스레드 단일 배달(_emit_pending)** — 워커/메인 발 emit 의 순서 역전과 락 안 emit 을 설계로 차단(보고서 3.1 해소).
3. **ParameterRunWorker 의 seq 기반 늦은 응답 폐기와 _Job 큐** — refresh/write/끊김/재부팅 취소가 모두 _stop_all 로 seq 를 올려 상태 머신 오염을 막는다. 클러스터 30대 상태를 장치당 1요청으로 읽는다.
4. **싱글턴 시그널 연결이 저장소 전체에서 바운드 메서드뿐** — 람다는 WinManager 의 자기 destroyed 처리 한 곳. WA_DeleteOnClose 창을 닫은 뒤 모든 싱글턴/Parameter 시그널을 발화해도 크래시 없음, 3회 재오픈 후 receivers 가 항상 1 → 0 으로 복귀(실측).
5. **QThread 소유 창 전부가 closeEvent 에서 cleanup/stop 직접 호출** — 서브클래스 오버라이드도 super().closeEvent 로 이어지고, 모든 워커가 aboutToQuit 에도 연결돼 MainWin 닫기 경로까지 덮인다(보고서 3.3 크래시 해소).
6. **spec_loader/ParamManager 가 nv2/nv1 스키마 오류를 예외 없이 load_errors 로 모아 대화상자+종료** — NV1 4단계에도 같은 규칙 적용. LocalSettingManager 의 _Setting 디스크립터는 시그널 누락을 클래스 생성 시점 TypeError 로 잡는다.
