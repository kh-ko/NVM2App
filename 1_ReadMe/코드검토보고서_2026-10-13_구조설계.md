# NVM2App 구조 설계·코드 디자인 검토 보고서 (4차)

- **작성 일자**: 2026-10-13
- **대상**: 커밋 df30779 작업 트리(clean)
- **검토 범위·관점**: 구조 설계(레이어·책임 배치·의존 방향·확장축)와 코드 디자인(계약·일관성·중복·검증 가능성). 세부 결함은 다루지 않는다 — 1~3차 보고서(F001~F111, N001~N133)의 영역이고, 그중 설계로 흡수된 항목은 이 보고서가 "반영됨/남음"으로만 언급한다.
- **방법**: b_core 전부, c_ui 의 골격(service_win / param_win / win_manager / main_win)·값 계층(c_values / d_param)·컨버터·창 9종, 2_resource 스키마 3종, tools(하네스·테스트 10종)를 직접 읽었다. import 그래프는 grep 으로 확인했다.
- **이전 보고서**: [3차 2026-09-28](코드검토보고서_2026-09-28.md) 5절(설계 방향) 을 기준선으로 삼아, 그 권고가 코드에 어떻게 실현됐는지와 그 다음 과제를 적는다.

## 1. 총평

**판정: 합리적이고, 이 규모(1인 유지보수 · 장비 제어 데스크톱 · Python/Qt · 앱 코드 약 20k줄)의 앱으로서 상위 수준의 구조다.** 특히 네 가지가 설계의 뼈대로서 제대로 서 있다.

1. **값 / 규약 / 바인딩 / 전송 4분리** — `Parameter`(값·상태·시그널) / `PacketSpec`(요청 생성·응답 판정) / `SpecRegistry`(param→spec) / `ServicePort`(문자열 왕복). 각 층이 아래층만 알고, 워커는 NV1/NV2 를 모르며 ServicePort 는 `p:` 를 모른다. 판정(`_judge`)과 적용(`apply_response` + `POLICY` 표)의 분리로 "새 프로토콜 = `_judge`/`build_request` 두 메서드" 가 성립한다.
2. **데이터 주도 스키마** — params.json(2,709) / nv2_spec.json(2,683) / nv1_spec.json 이 범위·접근·백업 대상·enable 조건·codec 문맥까지의 단일 출처이고, 템플릿(`expand`)과 로더 검증(`load_errors` → 기동 대화상자 → 종료)이 있다.
3. **UI 없는 워커 + 메인 스레드 모델 변경** — I/O 스레드는 바이트 왕복만 하고 `Parameter` 변경은 전부 메인 스레드에서 일어난다(`sig_result` 큐 배달 → `apply_response`). `Parameter` 에 락이 없어도 되는 올바른 이유다. seq 번호로 늦은 응답을 폐기하고, 백업·복원까지 같은 시퀀스 기계에 흡수해 상태 머신 밖의 I/O 경로를 없앴다.
4. **창 골격 단일화 + 검증 수단** — `ServiceWin`(2단계 초기화 `start()`, 잠금 단일 지점 `_sync_lock_state`, 생성 인자로 구성) 위에 창 7종이 같은 계약으로 올라가 있고, 하네스(런타임 격리·`ScriptedTransport`·좀비 연결 검사)와 차등 테스트가 구조 변경을 받쳐 준다.

3차 보고서 5.2 의 권고 8건은 **전부 코드에 반영**되어 있다(5절 표). 5.3 '유지' 항목과 5.4 '하지 않기로 한 것' 도 지켜졌다. 착수 순서(하네스 → 구조 변경)도 커밋 이력과 일치한다. 즉 설계 방향이 흔들리지 않고 실행되고 있다.

남은 구조적 과제는 "새 결함" 이 아니라 **"내린 선택의 대가"** 다. 우선순위 순으로:

- (4.1) 전역 싱글턴 9종과 import 시점 부수효과 — 의존·생성 순서가 코드에 암묵적으로 숨어 있고, 그 때문에 테스트가 프로세스 단위로만 격리된다.
- (4.2) 창별 워커 × 공유 직렬 버스 — 중재(기준 워커·대기 큐)가 워커 클래스 변수에 있고, 버스 우선순위를 제어할 지점이 없다.
- (4.3) 앱 수명 공유 `Parameter` 와 창별 편집 상태 — 한 창의 refresh 가 다른 창의 편집을 되돌리는 것이 구조에서 나온다(N092, 현행 유지 결정).
- (4.4) 확장축의 분산 — 표시 타입 하나를 더하면 5곳을 고친다.
- (4.5) 결정 기록이 docstring 에 누적되어 현재 계약과 역사가 섞인다.

어느 것도 큰 재작성이 아니다. 전부 S 규모 이동·표 치환·단언 추가 수준이다.

## 3. 잘 된 점 (유지할 것)

### 3.1 값 / 규약 / 바인딩 / 전송 4분리와 결과 계약
- `PacketSpec` 기본 클래스가 **정책(REASON→Verdict, Verdict→플래그·재시도)** 을 한 파일에 표로 갖고, 하위 클래스는 **지식(`_judge`, `build_request`)** 만 쓴다. NV2(1 param = 1 패킷) / NV1(n param = 1 패킷) / Raw(param 0) 세 형태가 같은 계약 아래 있다.
- 워커는 `Outcome.verdict` 하나로 다음 행동을 정하고 `reason` 은 로그에만 쓴다 — 워커에 프로토콜 사유 분기가 없다.
- `SpecRegistry` 가 param 객체를 dict 키로 쓰는 1회 조회(큐 생성 시) 와, `_Job` 에 spec 을 담아 응답 처리에서 재조회하지 않는 것은 단순하고 빠르다.

### 3.2 데이터 주도 스키마
- 값 정의(params.json) 와 전송 규약(nv2/nv1 spec) 을 파일로 분리했고, codec 문맥(어느 param 이 단위·범위를 주는가)까지 스키마가 선언한다. 코드(`codec.py`) 는 스키마 경로를 모른다.
- 템플릿(`expand`) 하나로 Cluster 30대분을 세 파일이 같은 규칙으로 펼친다.
- 로더의 '예외 없이 `load_errors` 로 모아 대화상자' 계약이 테스트·도구 호환까지 고려돼 있다.

### 3.3 워커
- UI 0, `StartResult` 반환, 대화상자·질문은 창 몫 — 1차 보고서의 핵심 권고가 완전히 실현됐다.
- `transport` 주입(`ParameterThread(transport)`) 한 지점으로 장비 없이 상태 전이 전체를 테스트한다(`test_worker_state.py` 9개 시나리오). 구조 변경의 안전망으로서 가장 값진 투자다.
- 백업(CAPTURE)·복원(RAW)을 시퀀스로 흡수해 `_Job.max_retry` 와 `SequenceReport` 로 재시도·누락·중단을 워커 한 곳에서 정한다. 창은 응답을 판정하지 않는다.

### 3.4 도메인 중립화와 변환 책임의 2층 분리
- `Parameter.value` = 물리량(Torr, %). 선로↔도메인은 b_core 의 codec, 도메인↔표시 단위는 c_ui 의 컨버터. 컨버터가 c_ui 에 있는 것은 이제 맞다(1차 보고서 2.2.1 은 해소됐다 — 물리 계산이 codec 으로 이사했으므로).
- 컨버터 시그널이 원인별 3종(표시 단위 / 자릿수 / 만압 문맥)이라 구독처가 필요한 것만 받는다. 차트가 자릿수 변경에 이력을 지우지 않는 것이 이 분리의 직접 효과다.

### 3.5 창 골격
- `ServiceWin` 계약 셋(2단계 초기화 / 잠금 단일 지점 / 생성 인자 구성)이 명확하고, "오버라이드 핸들러가 `super().__init__()` 중에 불린다" 류의 클래스 기본값 hack 이 사라졌다.
- 창은 `_sync_lock_state` 를 오버라이드하지 않고 `locked_actions() / edit_locked_actions()` 로 입력만 준다 — 정책이 한 곳, 데이터는 창에.
- `WinManager` 는 등록부 하나로 역할이 고정됐고, `start()` 훅 호출 위치(생성 직후·show 직전)가 명시돼 있다.

### 3.6 동시성 설계
- `ServicePort` 의 락 2단 분리(I/O 뮤텍스 / 정보 뮤텍스) 와 **메인 스레드 단일 배달**(`_pending_infos` → `_emit_pending`) 로 "워커 발 큐 배달 vs 메인 발 직접 배달" 의 순서 역전을 구조적으로 막았다. 주석이 왜 그런지를 정확히 설명한다.
- 싱글턴 9종의 생성 패턴(`threading.Lock` + `_initialized`)이 통일됐다(1차 1.1 해소).
- 워커 `cleanup()` 멱등 + `aboutToQuit`/`destroyed` 양쪽 연결, 창 `closeEvent` 가 명시 정리 — QThread fatal 의 뿌리가 닫혔다.
- 싱글턴 시그널에는 바운드 메서드만 연결(람다 금지) 규칙과 그것을 검사하는 `assert_no_zombie` 하네스가 짝을 이룬다.

### 3.7 UI 값 계층
- c_values(값 계약, 도메인 모름) ↔ d_param(param 바인딩) 분리가 선명하다. 활성 여부는 `_is_enabled_by_state` 한 곳(Not Support ∧ 값 조건 ∧ enable 조건)이 정하고 어느 경로도 `setEnabled(True)` 로 다른 경로를 되돌리지 않는다.
- Pres/Posi 표시 믹스인이 MRO 상 어디에 있어야 하는지(백업 훅의 `super()` 가 변환 없이 c_values 로 직행)를 docstring 이 전제 조건으로 못박고 테스트가 잡는다.

### 3.8 검증 수단
- 하네스: 런타임 경로 격리(`path_def` 덮어쓰기), 스크립트 transport, 창 파괴 뒤 시그널 발사로 좀비 검출, 대화상자 무음화. 러너가 끝에 `git status` 로 격리 누락을 잡는다.
- 차등 테스트(구버전 고정 사본 대비 126k 체크)로 "외부 동작 불변" 을 기계적으로 증명하며 구조를 바꿨다. 리팩토링의 모범 절차다.

### 3.9 문서 규율
- 모듈 docstring 이 계약·결정·근거·검토 ID 를 담고 있어 "왜 이렇게 했는가" 가 코드 옆에 있다. 1인 유지보수에서 가장 비싼 것이 바로 이 기억이다. (단, 4.5 의 비용이 있다.)

## 4. 구조적 약점과 설계 과제 (우선순위 순)

### 4.1 전역 싱글턴 9종 + import 시점 부수효과 — 의존과 생성 순서의 암묵화

**현황.** ParamManager · SpecRegistry · ServicePort · AppLogManager · LocalSettingManager · ConnectionSettingManager · PresConverterManager · PosiConverterManager · WinManager. 앱 코드에서 `X()` 호출이 약 135곳이고, 대부분 생성자 안에서 "가져다 쓴다".

생성 순서 의존이 코드에 숨어 있는 실례:
- `PresConverterManager.__init__` 이 `ParamManager()` 를 먼저 호출한다 — 주석 그대로 "의존하는 쪽이 의존 대상을 생성". 호출 순서가 바뀌면 codec 이 없다.
- `spec_registry.py:40`, `spec_loader.py:66` 의 모듈 수준 `_log = AppLogManager().get_logger(...)` — **import 자체가 로그 폴더 생성과 30일 정리라는 부수효과**를 낸다. 하네스가 "반드시 b_core 매니저 import 전에 `isolate_runtime()`" 을 요구하는 직접 원인이다.
- `ParameterThread.__init__` 의 기본 transport = `ServicePort()` — 워커를 만들면 포트 싱글턴이 생긴다.
- `run_tests.py` 가 테스트마다 서브프로세스를 띄우는 이유가 전부 여기서 온다(싱글턴·QApplication 이 섞이므로).

**평가.** 1인 데스크톱 앱에서 싱글턴 자체는 합리적이다(3차 5.3 유지 결정에 동의). 문제는 **"누가 언제 만드는가" 가 한 곳에 없다**는 것이다. 전면 DI 로 가자는 뜻이 아니다.

**제안(싱글턴을 유지한 채).**
1. **조립 지점 1곳** — `main.py` 가 AppLogManager → ParamManager(SpecRegistry·로더) → ServicePort → LocalSetting/ConnectionSetting → 컨버터 2종 순으로 **명시 생성**한다(지금은 ParamManager 까지만). 그 뒤의 `X()` 는 전부 '조회' 가 된다. 생성 순서 규칙을 코드 한 곳에서 읽을 수 있다.
2. 모듈 수준 `_log` 두 곳을 함수 안 지연 조회로 바꿔 **import 부수효과를 0** 으로. 하네스의 import 순서 제약이 사라진다.
3. 창·패널이 쓰는 싱글턴은 워커의 `transport=None` 처럼 **생성자 기본 인자**(`registry=None → SpecRegistry()`)로 열어 둔다. 앱 호출부는 바뀌지 않고, 테스트는 프로세스 분리 없이 대역을 꽂을 수 있다. 전부 바꿀 필요는 없고 테스트에서 교체가 필요한 것(ServicePort, SpecRegistry, LocalSetting)만.

### 4.2 창별 워커 × 공유 직렬 버스 — 중재가 워커 클래스 변수에

**현황.** 창마다 `ParameterRunWorker`(+QThread) 를 소유한다. MainWin 의 기준 워커 + Compound 고속 폴링 스레드(지연 없는 최대 속도) + 열린 창 수만큼의 유휴 모니터(100ms, Cluster Monitor 는 10ms) 가 `ServicePort._mutex` 하나를 경쟁한다. 우선순위는 없다 — 뮤텍스 획득 순서가 곧 버스 순서다.

중재 장치는 `ParameterRunWorker._primary / _pending_refresh` **클래스 속성**이다. "기준 refresh 중이면 다른 창의 refresh 는 PENDING, 끝나면 방출, 기준 워커가 사라지면 대기자 방출" 은 워커 인스턴스의 관심사가 아니라 **앱 수준 버스 중재**인데 워커 클래스 안에 있다. 테스트는 `is_primary=True` 를 넘겨야 하고, 기준 워커의 `cleanup()` 안에 대기자 방출이 끼어 있다.

**결과.** 창을 여러 개 열면 Compound scan-rate 가 비결정적으로 떨어진다. 상태바가 이를 보여 주지만, 설계상 **조정할 지점이 없다**(모니터 틱을 전역으로 늦추거나 Compound 에 우선권을 주려면 워커 여러 곳을 고쳐야 한다).

**평가.** '창 수명 = 워커 수명' 유지 결정(5.3)은 타당하다 — 격리·seq·log_source 가 1:1 소유를 전제한다. 바꿀 것은 소유가 아니라 **중재의 위치**다.

**제안.** `BusArbiter`(싱글턴 1개, b_core/e_worker_ver2) 가 `register_primary(worker)` / `request_refresh(worker) → OK|PENDING` / `release_pending()` / `discard(worker)` 를 소유하고, 워커는 그것을 부른다. 코드 이동 ~60줄. 워커의 책임이 "자기 시퀀스" 로 좁혀지고, 나중에 우선순위·스로틀(예: Compound 폴링 중 모니터 틱 2배)이 필요해지면 **그 객체 한 곳**만 바꾼다.

### 4.3 앱 수명 공유 `Parameter` 와 창별 편집 상태 (N092 — 현행 유지 결정)

**현황.** `Parameter` 는 앱 수명 단일 객체다. 어느 창의 refresh 든 읽기 성공마다 `notify_synced()` → 같은 param 을 바인딩한 **모든 창**의 위젯이 `set_value + commit` → 다른 창에서 편집 중이던 값이 장비값으로 돌아가고 dirty 가 지워진다. `ParamWidget._bind_param` 은 `sig_synced` 를 발신자 구분 없이 commit 에 연결한다(주석 "N092 현행 동작 유지").

**평가.** "값 캐시(Parameter)" 와 "편집 버퍼(위젯 `ori_value`)" 라는 두 개념의 경계가 시그널 하나로 뭉개진 **구조 문제**다. 하나의 `Parameter` 를 공유하는 설계 자체는 옳다(캐시 일관성·Compound ref 갱신·문맥 param 공유가 모두 그것을 전제). 고칠 것은 sync 통지의 **의미**다.

**제안(작다).** `notify_synced(origin)` 에 발신 워커를 싣고, `ParamWidget` 이 소속 워커(창이 알고 있음)를 알게 한다. 자기 창의 sync 가 아니면 dirty 위젯은 **표시값만 갱신하고 commit 하지 않거나 건너뛴다**. 사용자 결정으로 보류된 항목이므로 과제로만 기록한다.

### 4.4 확장축이 흩어져 있다 — 표시 타입 1개 추가 = 5곳

**현황.** 새 display type 을 더하려면: `general_enum`(`ParamDisplayType` + `PARAM_DISPLAY_TYPE_MAP`) → `Parameter.__init__` 의 16-분기 `elif` 와 `_init_xxx` → (필요 시) c_values 위젯 → `param_values` 거울 클래스(RO/RW/WO 최대 3개) → `param_folder_widget` 의 (type, acc) 사다리(100줄). 거울 클래스를 독립으로 두는 것은 결정(5.3)이라 존중한다.

**제안(결정과 충돌하지 않는 것만).**
- `param_folder_widget` 의 사다리를 `{(ParamDisplayType, ParamAccType): 위젯 클래스}` **표** 로. 미지원 조합이 '표에 없음' 으로 드러나고(N091 류 조용한 누락이 구조적으로 사라짐), 추가는 1줄이다. 사다리의 `pass` 분기 12개가 바로 그 '없음' 들이다.
- `Parameter._init_*` 16분기도 `{ParamDisplayType: (data_type, 범위 정책)}` 표로 줄일 수 있다. 특수 초기화(enum/errnum/btn)만 함수로 남긴다.

### 4.5 결정 기록이 docstring 에 누적 — 현재 계약과 역사의 혼재

**현황.** `parameter_run_worker.py` docstring 77줄, `service_win.py` 39줄, `packet_spec.py` 41줄 중 상당 부분이 "2026-09-10 1단계 … 2026-10-12 결과 계약 … 전에는 … 지금은 …" 의 변경 이력이다. 신규 독자는 '지금의 계약' 을 역사에서 추출해야 한다. 3차 보고서 4절 9 (문서-코드 불일치 16건)의 뿌리이기도 하다 — 역사는 코드가 바뀌어도 함께 바뀌지 않는다.

**제안.** `1_ReadMe/decisions.md` 에 ADR 형식(번호·날짜·결정·근거·기각된 대안)으로 역사를 옮기고, docstring 은 **현재 계약 + "결정 #n"** 참조만 남긴다. 결정에 이미 ID(결정 A~K, F/N 번호, "2026-10-12 사용자 결정")가 있어 이전 비용은 작다. 3차 보고서 5.3/5.4 의 '유지·기각' 목록이 그대로 ADR 의 씨앗이다.

### 4.6 백업 형식의 정체성 모델이 둘

- ParamWin Save/Load File: JSON `{path, name, value, unit}` — 결정 B(경로가 정체성, 프로토콜 id 는 기록하지 않는다).
- Backup/RestoreWin: 텍스트 `"<path>.<name>, p:01<id><idx><value>"` — 선로 원문(복원이 spec 과 독립, R5).

같은 앱에 **두 정체성 모델**이 공존한다. 후자는 NV2 전용이라(`build_request_line` 은 `Nv2WriteSpec` 에만 있다) NV1 param 이 백업 대상이 되는 순간(결정 10) 성립하지 않는다. 지금 결정할 일은 아니고 3차 5.4 에 이미 트리거가 적혀 있다. 구조 그림(2절) 에 '두 포맷' 이 있다는 사실만 명시해 두면 된다.

### 4.7 MainWin 의 위치와 중복 선언

- `ServiceWin` 골격 밖의 유일한 창(믹스인 직접 상속)이다. 앱 수명 창이라 2단계 초기화가 필요 없고, 골격의 `closeEvent`(워커 cleanup) 대신 `aboutToQuit` 에 기대는 것도 일관된 이유가 있다. 다만 "골격 밖" 이라는 사실을 docstring 에 적어 두는 것이 좋다(지금은 없다).
- 674줄: 툴바 47개 1:1 연결, param 40개 조회, Compound 슬롯 조립, ParamWin 런치 슬롯 30개(8 kwargs 반복). 1:1 슬롯·카탈로그 표 기각은 사용자 선호(5.4)이므로 존중한다. 책임 분리 관점에서 뽑아낼 수 있는 것 둘:
  - Compound 슬롯 조립(`_COMPOUND_REF_PATHS` + pairs + `CompoundData` 팩토리)을 작은 모듈로(F072 로 이미 지목).
  - **문맥 param init 목록 28개가 두 번 선언된다** — 한 번은 코드(MainWin `add_init_param_ptr` 28줄), 한 번은 스키마(nv2_spec.json `codecs` 절 → `Codec.context_params`). 둘이 어긋나도 아무도 모른다. 5.4 가 제안한 "`codec.context_params` ⊆ MainWin init 목록" 단언이 tools 에 **아직 없다**(grep 0건). 20줄짜리 테스트 하나로 닫힌다.

### 4.8 규칙의 기계적 보장이 없다

레이어 규칙(b_core→c_ui 금지), 바운드 메서드 연결 규칙, x_message 표시 전용 규칙이 전부 "주석 + 리뷰" 로만 유지된다. 지금은 0건이지만 보장 장치가 없고, CI 도 없다(`.github` 없음, `run_tests.py` 수동).

**제안.** tools/tests 에 ① `ast` 로 b_core 안 `c_ui` import 0건 단언, ② 싱글턴 시그널에 `.connect(lambda` 0건 단언 — 둘 다 20줄. CI 는 ftd2xx.dll 이 Windows 전용이라도 `run_tests.py` 는 offscreen 으로 돌므로 GitHub Actions windows runner 하나면 된다.

### 4.9 코드 디자인 소항목

- **6연타 슬롯**: setpoint01~06 × (패널 2 + 로컬 설정 창 2) 와 `LocalSettingManager` 시그널 12개. `_Setting` 디스크립터 덕에 **선언**은 2줄이지만 **소비**는 창마다 6~12 슬롯이 복제된다. 바운드 메서드 규칙을 지키면서 줄이는 길: 행 하나를 QObject 자식(`_SetpointRow(index)`) 으로 만들어 자기 슬롯을 갖게 하면 창과 함께 파괴되어 좀비가 없다.
- **거울 클래스 생성자가 문자열 경로를 받아 재조회**: `ParamFolderWidget` 은 이미 `Parameter` 객체를 들고 있는데 `f"{path}.{name}"` 으로 문자열을 만들어 넘기고 `ParamWidget._resolve_param` 이 `ParamManager()` 에서 다시 찾는다. `Parameter` 객체를 직접 받으면 이중 조회와 d_param 의 ParamManager 의존이 사라진다(d_param 은 `Parameter` 만 알면 된다).
- **`ParamWin.on_clicked_write_only_component` 의 `isinstance` 분기 2개**: 앱 전체에서 유일한 타입 분기다. WO 위젯에 `write_value()` 훅 하나를 두면 사라지고 c_values 계약과 일관된다.
- **ParamWin 생성자 위치 인자 10개 + 서브클래스 3곳이 전부 재나열**: 호출부 30곳이 이미 전부 키워드로 부르므로 `*` 로 keyword-only 로 바꾸는 비용은 0 이고, 순서 실수를 구조적으로 막는다.
- **죽은 코드 잔존**(2·3차 지적, 아직 남음): `Parameter.visible_conditions / set_visible_condition / INT_TYPES 등 튜플 4개`(같은 튜플이 `TextCodec` 에 있음), `ParamManager.get / get_all / get_all_folder_paths`, `general_enum` 의 `MainChart*`. 구조 영향은 없지만 "스키마 `visible` 키가 로드만 되고 소비되지 않는다" 는 계약 오해를 부른다 — 지우거나 로더가 거부해야 한다.
- **`_ver2` 접미사 폴더**(`e_worker_ver2`, `b_control_ver2`, `c_window_ver2`): ver1 폴더가 사라져 정보가 없다. 정렬 접두(a_~h_) 유지는 결정(5.3)이라 존중한다. import 전체에 닿으므로 '언젠가' 항목.
- **x_message 와 창 내 `QMessageBox` 직접 호출 공존**은 결정(5.3)이다. 문구 중복만 주의하면 된다(현재는 겹치지 않는다).
