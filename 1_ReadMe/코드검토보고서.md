## 3. 멀티 쓰레드 환경에서의 자원 해제 및 경합 (Thread Safety & Concurrency)

### 🚨 3.1 [위험] `ServicePort`의 `_pending_infos` 락 누락에 따른 Race Condition
하드웨어 통신 단일 통로인 [ServicePort](file:///e:/04_Working/01_APC_VALVE/004_NVM2App/01_Working/SW/NVM2App/b_core/d_dal/service_port.py)에서 심각한 동시성 버그가 존재합니다.

```python
# service_port.py (Line 54 ~ 70)
def _set_connect_info(self, info: str):
    """반드시 _mutex 안에서 호출. 시그널은 락 해제 후 _flush_connect_signals() 가 발화."""
    if self._connect_info == info:
        return
    self._connect_info = info
    self._pending_infos.append(info)  # 🔒 _mutex 보호 하에 실행

def _flush_connect_signals(self):
    """락 해제 후 호출 — 뮤텍스 안에서 쌓인 connect_info 변경을 순서대로 emit."""
    while True:
        try:
            info = self._pending_infos.pop(0)  # ❌ 락 없이 실행됨!
        except IndexError:
            return
        self.connect_info_changed.emit(info)
```

- **발생 원인**:
  - `request()`([L128](file:///e:/04_Working/01_APC_VALVE/004_NVM2App/01_Working/SW/NVM2App/b_core/d_dal/service_port.py#L128)), `open()`([L72](file:///e:/04_Working/01_APC_VALVE/004_NVM2App/01_Working/SW/NVM2App/b_core/d_dal/service_port.py#L72)), `close()`([L112](file:///e:/04_Working/01_APC_VALVE/004_NVM2App/01_Working/SW/NVM2App/b_core/d_dal/service_port.py#L112))는 `_mutex`를 푼 직후 `_flush_connect_signals()`를 호출합니다.
  - [CompoundPollThread](file:///e:/04_Working/01_APC_VALVE/004_NVM2App/01_Working/SW/NVM2App/b_core/e_worker_ver2/compound_run_worker.py#L52)와 [ParameterThread](file:///e:/04_Working/01_APC_VALVE/004_NVM2App/01_Working/SW/NVM2App/b_core/e_worker_ver2/parameter_run_worker.py#L80), 그리고 메인 스레드가 `ServicePort`를 동시에 호출할 수 있습니다.
  - 한 스레드가 통신 실패로 `_close_internal()`을 호출하여 `_pending_infos.append("")`를 한 직후 락을 풀고 `_flush_connect_signals()`에 진입하는 순간, 다른 스레드가 `request()`나 `open()` 후 동시에 `_flush_connect_signals()`에 진입할 수 있습니다.
  - 일반 파이썬 리스트인 `_pending_infos`에 대해 **동시에 `pop(0)`을 시도하거나 `append`와 `pop`이 락 없이 교차**하여 `IndexError`, 시그널 누락, 순서 뒤바뀜이 발생합니다.

- **해결 방안 (원자적 버퍼 복사 후 emit)**:
```python
def _flush_connect_signals(self):
    """뮤텍스 안에서 대기 목록을 로컬로 원자적 이동한 뒤 락 외부에서 순차 emit."""
    with QMutexLocker(self._mutex):
        if not self._pending_infos:
            return
        to_emit = list(self._pending_infos)
        self._pending_infos.clear()

    for info in to_emit:
        self.connect_info_changed.emit(info)
```

### 3.2 단일 시리얼 버스 경합 및 통신 타임아웃 지연
- 물리 RS232 통신 회선은 단 1개인데, [CompoundPollThread](file:///e:/04_Working/01_APC_VALVE/004_NVM2App/01_Working/SW/NVM2App/b_core/e_worker_ver2/compound_run_worker.py#L119)는 인위적 지연 없이 최대 속도로 `p:29` 폴링 루프를 돕니다.
- 사용자가 UI에서 버튼(예: Open/Close/Hold/SetPoint)을 조작하면 [ParameterThread](file:///e:/04_Working/01_APC_VALVE/004_NVM2App/01_Working/SW/NVM2App/b_core/e_worker_ver2/parameter_run_worker.py#L91)가 쓰기 요청을 위해 `ServicePort._mutex`를 얻으려 대기해야 합니다.
- 만약 통신 노이즈나 일시적 지연으로 `Serial.read_until()`의 타임아웃(0.5초)이 발생하면, **한 스레드가 뮤텍스를 500ms 동안 쥐고 있게 됩니다.** 이로 인해 다른 스레드의 통신 요청이 블로킹되어 UI 체감 반응성이 순간적으로 저하될 수 있습니다.
- 또한 `_request_locked`에서 매 요청마다 `reset_input_buffer()`를 호출하므로 이전 지연 응답 잔여 바이트는 제거되지만, 타임아웃 동안의 락 점유 시간은 통신 속도에 큰 영향을 줍니다.

### 3.3 메인 윈도우 종료 시 스레드 자원 해제 누락 및 비정상 크래시
- [MainWin](file:///e:/04_Working/01_APC_VALVE/004_NVM2App/01_Working/SW/NVM2App/c_ui/c_window_ver2/a_main/main_win.py)은 `closeEvent`를 정의하지 않고 있습니다.
- 사용자가 윈도우 우상단 'X'를 눌러 종료할 때:
  1. `MainWin` 인스턴스 소멸 시작.
  2. 자식 `QObject`들이 파괴되는 도중 백그라운드의 [CompoundPollThread](file:///e:/04_Working/01_APC_VALVE/004_NVM2App/01_Working/SW/NVM2App/b_core/e_worker_ver2/compound_run_worker.py)와 [ParameterThread](file:///e:/04_Working/01_APC_VALVE/004_NVM2App/01_Working/SW/NVM2App/b_core/e_worker_ver2/parameter_run_worker.py)는 여전히 루프/이벤트 대기 상태로 동작.
  3. 부모 객체 소멸로 인해 `QThread: Destroyed while thread is still running` 또는 C++ 포인터 해제 후 접근으로 인한 Python 런타임 Fatal Crash 발생 위험.
- **해결 방안**:
  [MainWin](file:///e:/04_Working/01_APC_VALVE/004_NVM2App/01_Working/SW/NVM2App/c_ui/c_window_ver2/a_main/main_win.py)에 명시적인 `closeEvent`를 구현하여 모든 스레드를 정지 및 대기(`wait()`)시킨 후 종료해야 합니다.
  ```python
  def closeEvent(self, event):
      self.compound_timer.stop()
      if hasattr(self, 'compound_worker'):
          self.compound_worker.stop()
      if hasattr(self, 'param_worker'):
          self.param_worker.cleanup()
      super().closeEvent(event)
      event.accept()
  ```

### 3.4 `PortScanThread`의 블로킹 포트 오픈과 종료 응답성
- [PortScanThread.run()](file:///e:/04_Working/01_APC_VALVE/004_NVM2App/01_Working/SW/NVM2App/b_core/e_worker_ver2/comport_scan_run_worker.py#L35)은 PC의 모든 시리얼 포트를 순회하며 `serial.Serial(...)`을 직접 엽니다.
- 만약 블루투스 가상 COM 포트나 응답 없는 드라이버가 물려 있는 경우, `serial.Serial()` 생성자 자체(OS 레벨 포트 핸들 오픈)가 수 초 동안 블로킹될 수 있습니다.
- 사용자가 스캔 중 창을 닫으려 할 때 `self._is_running = False` 플래그는 포트 간 루프 진입 시에만 검사되므로, 블로킹 I/O 중에는 즉각 중단되지 않고 대기 팝업("Please wait for the previous scan to complete...")이 오랫동안 유지되는 현상이 발생할 수 있습니다.
